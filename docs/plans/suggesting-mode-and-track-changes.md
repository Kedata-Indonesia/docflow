# Design — Suggesting mode & Track Changes

> **Status:** design proposal (not implemented). Tracks issues
> [#27](https://github.com/Kedata-Indonesia/docflow/issues/27) (document modes)
> and [#28](https://github.com/Kedata-Indonesia/docflow/issues/28) (track changes
> / review suggested edits).
> **Audience:** library implementers + host integrators.
> **Scope:** library-side design (`packages/plugins`, `packages/vue`,
> `packages/core`). Host responsibilities are called out explicitly.

## 1. Problem

Today the editor is binary: editable or not (`<DocsEditor :editable>`). There is
no way to review changes without letting the reviewer edit the document
directly, and no record of *who* proposed *what*. Users expect the Google-Docs
trio: **Editing · Suggesting · Viewing**, with suggestions that can be
accepted/rejected, and a Tools entry to review them.

## 2. Goals / non-goals

**Goals**
- A controlled **document mode**: `editing | suggesting | viewing`.
- Suggesting mode records edits as **suggestions** (insert/delete, later
  formatting) instead of applying them, inside the collaborative document.
- **Accept/reject** per suggestion and for all suggestions.
- A **review surface** listing suggestions with author + accept/reject.
- Everything survives Yjs collaboration, and coexists with comment marks,
  citations, and footnotes.

**Non-goals (this design)**
- Suggestion threads/comments on a suggestion (v2).
- Server-side suggestion collections or RBAC changes (host concern; see §9).
- Real-time "suggestion cursor" awareness beyond the existing peer cursors.

## 3. Document modes

Introduce one controlled prop on `<DocsEditor>`:

```ts
type DocumentMode = 'editing' | 'suggesting' | 'viewing'
props.mode?: DocumentMode            // default 'editing'
emits('update:mode', mode: DocumentMode)
```

Semantics:

| Mode | Editor editable? | Edits become |
|------|------------------|--------------|
| `editing` | yes | document changes (today's behaviour) |
| `suggesting` | yes (so the caret works) | suggestion marks (§4) |
| `viewing` | no (`setEditable(false)`) | nothing (read-only) |

- `mode` **supersedes** the raw `editable` prop as the intent; keep `editable`
  working for backwards compatibility (map `editable === false` → `viewing`
  when `mode` is unset). Document the precedence in `LIBRARY_CONTRACT`.
- Reactivity: switching mode must not remount the editor (caret/undo/collab
  preserved) — `setEditable` + a plugin-state flag, not a `key` change.

Wiring:
- **View menu** gains a "Document mode" group (radio, `checked` state):
  `mode-editing` / `mode-suggesting` / `mode-viewing`. `HeaderBar` already
  supports `checked` items; the actions flow through the existing
  `menu-click` emit and are handled by `DocsEditor`.
- A small status chip ("Suggesting") near the title; the toolbar's edit
  controls stay enabled in suggesting mode.

## 4. Data model — suggestion marks

Suggestions live **in the document** as ProseMirror **marks**, exactly like the
comment mark (`packages/plugins/src/comment.ts`). This is what makes them
collaborative for free: marks are part of the Yjs-synced doc, so every client
sees suggestions converge, and persistence needs no new server collection.

Three marks (phased):

```ts
'suggestion-insert'  attrs: { suggestionId, authorId, authorName, createdAt }
'suggestion-delete'  attrs: { suggestionId, authorId, authorName, createdAt }
'suggestion-format'  attrs: { suggestionId, authorId, authorName, createdAt, before, after }  // P3
```

- `suggestionId` groups a run of edits into one reviewable unit (a typed word,
  a deleted phrase). UUID generated by the client; collisions are vanishingly
  unlikely and the mark is idempotent.
- `authorId/Name` denormalised on the mark (same pattern as the comment mark) so
  the review UI needs no lookup and old documents stay readable.
- **Excludes:** the two marks exclude each other (`excludes: 'suggestion-delete'`
  etc.); they must **not** exclude `comment`/`citation` marks.
- Do **not** store proposal text on the mark — the marked range *is* the text.

### Why marks, not nodes

Nodes would break ProseMirror's inline content model on accept/reject and
complicate splitting. Marks keep the underlying text intact, so reject/accept is
a pure mark/range operation.

## 5. Commands

A `suggestChangesPlugin` (`packages/plugins`) exposes (namespaced, non-Throw):

| Command | Effect |
|---------|--------|
| `setDocumentMode(mode)` | flips plugin state (§3) |
| `acceptSuggestion(id)` | insert-mark → drop mark (keep text); delete-mark → delete range |
| `rejectSuggestion(id)` | insert-mark → delete range; delete-mark → drop mark (keep text) |
| `acceptAllSuggestions()` / `rejectAllSuggestions()` | apply per suggestion, one transaction each (undoable) |
| `suggestionCount()` | for the badge |

Rules:
- Each accept/reject is a normal, **undoable, collaborative** transaction.
- `acceptAll` iterates a snapshot of ids (stable order) so results are
  deterministic across clients.
- Commands are exposed on `editor.commands` **and** `pluginActions` so hosts can
  drive them programmatically (same duality as `insertCitation`).

## 6. Capturing edits in suggesting mode

A ProseMirror plugin (`appendTransaction` + `handleKeyDown`/`handleDOMEvents`):

- **Insertions** (typing, paste, IME commit): when `mode === 'suggesting'`, wrap
  the inserted range in `suggestion-insert` with a fresh `suggestionId`.
  Implementation detail: detect inserted ranges from `tr.steps`/`tr.mapping`
  rather than intercepting every key, so paste and IME work.
- **Deletions** (Backspace/Delete, cut, selection replace): do **not** remove
  the text — apply `suggestion-delete` to the range instead. Selection-replace =
  delete-mark + insert-mark in one transaction (one `suggestionId`).
- **Not captured:** moving the caret/selection, formatting in P1 (P3 adds
  `suggestion-format`), table structural edits (decide per case).
- Guard rail: the plugin only rewrites transactions whose `meta` says they came
  from user input; programmatic/host transactions (AI insert, collaboration
  apply) are left alone, mirroring how the AI plugin gates its writes.

Edge cases to test: IME composition, multi-range paste, cut, delete across
marks, undo/redo inside suggesting mode, collab echo (a remote edit must not be
re-tagged locally).

## 7. UI

- **View → Document mode** (radio) + status chip (§3).
- **Tools → Review suggested edits** opens the review surface.
- **Review surface:** a sidebar (reuse the sidebar stack) listing suggestions —
  author avatar/name, type (insert/delete), the proposed text snippet, and
  Accept / Reject buttons, plus **Accept all / Reject all**. This needs a new
  `SidebarKey` value (e.g. `'review'`) — a small, additive library change to
  `types.ts` + `DocsEditorSidebars.vue` (the extension-point discussion in #22
  applies: hosts that want a custom review UI should use the same slot pattern).
- Empty state: "No suggestions".

## 8. Collaboration

- Marks ride the Yjs doc → suggestions converge; no extra protocol.
- Concurrent accept/reject of the *same* `suggestionId` converge (last write
  wins per range) because both resolve to the same mark/range operation.
- Awareness: the existing peer cursor colours already tell reviewers who is who;
  a per-suggestion author label covers attribution.
- The `suggestionId` must be created **once** at the first edit and reused for
  the whole run, otherwise each keystroke becomes a separate suggestion.

## 9. Permissions (host-owned)

The library stays auth-agnostic. It provides commands + UI, and the **host**
decides who may use them:

- Hosts gate Suggesting mode behind their role model (`viewer`/`commenter`/
  `editor`/`owner` in `docflow-app`). A `commenter` might be allowed to
  *suggest*; accept/reject should require `editor`/`owner`.
- Library-side knob: an optional `canReviewSuggestions` prop (or reuse the host's
  `editable`) to hide the Accept/Reject UI for roles that may not review.
- **Never** enforce permissions in `packages/*` — that breaks the contract.

## 10. Persistence

- v1: **nothing new on the server** — suggestions are marks in the document
  (`Document.content` derived read-model + Yjs). Export/print must decide how to
  render them (§11).
- Optional later: denormalise a suggestions index (per document) for dashboards
  ("3 pending suggestions"). Add only when a host needs it.

## 11. Export / print

A suggestion is not final text. Recommended:
- Provide an export option `suggestions: 'accept' | 'reject' | 'annotate'`
  (default **accept** = export the document as if all suggestions were accepted).
- `annotate` renders insertions/deletions with markup for review PDFs.
- Keep this in the export layer (`packages/export`), not the editor.

## 12. Library boundary

| Concern | Where |
|---------|-------|
| Suggestion marks, capture plugin, commands | `packages/plugins` |
| `mode` prop, View/Tools menu items, review sidebar, status chip | `packages/vue` (+ `SidebarKey`) |
| `mode` plumbing / plugin state | `packages/core` (EditorOptions) |
| Auth, roles, persistence, publish | **host** (`docflow-app`) |
| Export rendering of suggestions | `packages/export` |

New/changed public surface: `mode` prop + `update:mode` emit, `'review'`
SidebarKey, plugin commands, `DocumentMode` type. All **additive**.

## 13. Phasing

| Phase | Deliverable | Acceptance |
|-------|-------------|-----------|
| **P1** | `mode` prop + View menu modes; `suggestion-insert`/`-delete` marks; capture on type/paste/backspace; per-suggestion accept/reject commands | In suggesting mode, typing/deleting produces marks, not edits; accept/reject resolves them; editing/viewing unchanged |
| **P2** | `Tools → Review` + review sidebar (list, accept/reject, accept/reject all), status chip | A reviewer can clear all suggestions without touching the doc directly |
| **P3** | `suggestion-format` (formatting changes) + table structural cases | Formatting suggestions accept/reject |
| **P4** | Export modes (`accept`/`reject`/`annotate`) in `packages/export` | Export honours the chosen suggestion mode |

## 14. Testing

- **Unit (plugins):** capture inserts/deletes from a synthetic transaction;
  accept/reject per type; accept-all determinism; mark excludes; IME/paste
  synthetic events; undo/redo.
- **Unit (vue):** mode prop → `setEditable` + plugin state; menu actions; review
  sidebar list/empty; existing comment/citation tests must stay green.
- **E2E (playground):** add a "Suggesting" review scenario — type (green),
  delete (strikethrough), accept one, reject one, accept-all.
- **Regression:** editing-mode output is byte-identical to today for existing
  documents (no marks added when `mode === 'editing'`).

## 15. Open questions

1. **Commenter role** — may a `commenter` create suggestions? (Host policy; the
   library just needs to not block it.)
2. **Suggestion ids across offline edits** — client UUID + Yjs merge is fine, but
   confirm no duplicate-id grouping issues after an offline/reconnect.
3. **`suggestion-format` scope** — mark-level formatting only, or block attributes
   too (alignment, headings)?
4. **Menu extension point** — View/Tools items are hardcoded in `HeaderBar`
   today. Either add them directly (recommended for core features) or introduce a
   plugin menu-contribution point (bigger; separate issue).
5. **Reuse `editable` or introduce `mode`** — proposal keeps both, `mode` wins.
